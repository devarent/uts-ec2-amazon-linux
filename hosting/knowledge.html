00 · Orientasi

Cara memakai halaman ini

Halaman ini disusun seperti runbook: bagian awal menjelaskan urutan belajar, bagian tengah berisi konfigurasi yang benar-benar dipakai di lab, dan bagian akhir berisi cara mencari masalah saat deployment gagal. Gunakan daftar isi di kiri untuk melompat.

Konteks tugas. Website portofolio ini adalah hasil UTS Cloud Computing Program Studi Teknologi Informasi, Universitas Darma Persada. Identitas: Muhammad Arya Fatthurahman, NIM 2023230006, kelas TIFM. Target deployment: AWS EC2 dengan alamat publik (bukan localhost), web server Nginx/Apache2, Security Group SSH 22 + HTTP 80.

Tiga jalur yang bisa dipakai

1. Jalur statis (dipakai sekarang)

Paling cepat dan paling aman untuk penilaian.

  • index.html + assets/ disalin ke docroot
  • Nginx/Apache2 menyajikan file langsung
  • Portal login berjalan di sisi browser (localStorage)
  • Tidak butuh Node.js, database, atau container

2. Jalur Dinamis (lokal)

Next.js + PostgreSQL dari folder app/.

  • next dev / next start di port 3000
  • API auth, guestbook, health check
  • Reverse proxy Nginx dari 80 ke 3000
  • Cocok untuk demonstrasi fitur CRUD

3. Jalur container (opsional)

Docker Compose → Kubernetes/Helm.

  • Image multi-stage, health check
  • Compose untuk satu VM
  • Deployment + Service + Ingress di K8s
  • Helm chart di folder helm/

Perintah verifikasi cepat

terminal — dari komputer sendiricurl -I http://IP-PUBLIK/ curl -s http://IP-PUBLIK/ | head -20 nslookup domain-anda

Jika curl -I mengembalikan HTTP/1.1 200 OK, berarti DNS dan web server sudah benar. Kalau Connection refused, periksa Security Group dan status service. Kalau timed out, biasanya port 80 belum dibuka.

03 · AWS

AWS Cloud-Native Architecture Handbook — 30 topik

Rangkuman 30 topik yang saya jadikan acuan saat merancang deployment EC2. Bagian ini bukan salinan buku, melainkan catatan pribadi yang sudah disederhanakan dan dikaitkan dengan praktik di lab.

IAM→ VPC→ EC2 / ECS→ RDS / S3→ CloudWatch→ Route 53

Bagian A · Dasar cloud dan identitas (topik 1–6)

1–3. Model layanan, infrastruktur global, dan IAM

1. Model layanan. IaaS memberi kontrol penuh (EC2), PaaS mengelola runtime (Elastic Beanstalk/App Runner), SaaS langsung dipakai. Semakin managed, semakin sedikit operasi tetapi semakin sedikit kontrol.

2. Infrastruktur global. Region adalah area geografis, Availability Zone adalah beberapa data center terpisah di dalam region. Untuk latihan pilih region terdekat (ap-southeast-3 Jakarta atau ap-southeast-1 Singapura) agar latensi rendah.

3. IAM. User untuk manusia, role untuk service, policy sebagai dokumen izin. Prinsip least privilege: mulai dari izin minimum, tambah hanya jika perlu. Jangan pernah menaruh Access Key di kode atau repo.

aws cli — cek identitas, jangan pakai rootaws sts get-caller-identity aws iam list-attached-user-policies --user-name NAMA_USER aws configure list
4–6. VPC, pilihan compute, dan pilihan storage

4. VPC. Jaringan privat virtual. Subnet publik punya route ke Internet Gateway; subnet privat keluar lewat NAT Gateway. Security Group bersifat stateful dan melekat pada resource; Network ACL stateless dan melekat pada subnet.

5. Compute. EC2 untuk kontrol penuh, Lambda untuk event kecil, ECS/EKS untuk container, App Runner untuk aplikasi web sederhana. Untuk tugas ini EC2 paling sesuai karena harus menunjukkan konfigurasi web server dan IP publik.

6. Storage. EBS untuk disk instance, S3 untuk object, EFS untuk file system bersama. S3 bukan disk untuk database dan bukan tempat menyimpan file yang butuh locking.

Aturan praktis: satu EC2 di subnet publik sudah cukup untuk UTS. Jangan membangun VPC multi-tier kalau belum bisa menjelaskan biaya dan cara membersihkannya.

Bagian B · Compute dan jaringan (topik 7–12)

7–9. Siklus EC2, AMI/EBS, dan Elastic Load Balancing

7. Siklus EC2. pending → running → stopping → stopped → terminated. Instance stopped tidak dikenai biaya compute tetapi EBS tetap ditagih. Terminated menghapus instance; volume root ikut terhapus kecuali diatur lain.

8. AMI dan EBS. AMI adalah template (OS + snapshot). EBS adalah volume jaringan; snapshot disimpan di S3 dan bisa dibuat image. Ganti tipe volume gp2 → gp3 biasanya lebih murah dan cepat.

9. ELB. Application Load Balancer untuk HTTP/HTTPS layer 7, Network Load Balancer untuk TCP layer 4. Health check menentukan instance mana yang menerima trafik. Untuk satu instance, ALB tidak wajib.

10–12. Auto Scaling, Route 53, dan CloudFront

10. Auto Scaling. Launch template + grup + kebijakan scaling. Untuk lab matikan atau batasi minimum 1 agar tidak ada instance tak terduga.

11. Route 53. Record A mengarah ke IPv4, AAAA ke IPv6, CNAME ke nama lain. Untuk IP publik EC2 gunakan A record. TTL kecil (60–300 detik) memudahkan perubahan saat lab.

12. CloudFront. CDN dengan cache di edge. Untuk website statis ini bisa mempercepat global, tetapi menambah kompleksitas invalidasi. Tidak wajib untuk UTS.

Bagian C · Data dan storage (topik 13–17)

13–15. RDS, DynamoDB, dan S3 lifecycle

13. RDS. Database managed: backup otomatis, patching, multi-AZ. Letakkan di subnet privat dan hubungkan lewat Security Group, bukan IP publik.

14. DynamoDB. NoSQL key-value, cocok untuk session atau data akses tinggi dengan pola key jelas. Bukan pengganti otomatis untuk query relasional kompleks.

15. S3 lifecycle. Transisi ke Standard-IA atau Glacier, lalu expiry. Aktifkan versioning untuk perlindungan tidak sengaja hapus, dan blok public access kecuali memang hosting statis.

16–17. ElastiCache dan strategi backup

16. ElastiCache. Redis/Memcached managed untuk cache, session, queue ringan. Selalu siapkan fallback jika cache mati.

17. Backup. Tentukan RPO (toleransi kehilangan data) dan RTO (lama pemulihan). Uji restore, bukan hanya membuat backup. Untuk lab, snapshot manual sebelum eksperimen berisiko.

Bagian D · Operasi dan delivery (topik 18–23)

18–20. CloudWatch, CloudTrail, dan AWS Config

18. CloudWatch. Metrik (CPU, network), log group, alarm, dashboard. Agen CloudWatch diperlukan untuk memori dan disk di level OS.

19. CloudTrail. Jejak siapa melakukan apa lewat API. Aktifkan di semua region untuk audit.

20. AWS Config. Mengevaluasi kepatuhan resource terhadap aturan, misalnya “tidak boleh ada bucket publik”.

cloudwatch agent — cek statussudo systemctl status amazon-cloudwatch-agent sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -m ec2 -a status aws logs describe-log-groups --region ap-southeast-1
21–23. CodePipeline, IaC AWS, dan ECS/EKS

21. CodePipeline. Source (CodeCommit/GitHub) → Build (CodeBuild) → Deploy (CodeDeploy/ECS). Alternatif yang lebih umum di industri: GitHub Actions.

22. IaC AWS. CloudFormation dan CDK adalah native AWS; Terraform/OpenTofu lebih portabel. Pilih satu dan konsisten.

23. ECS/EKS. ECS lebih sederhana tanpa Kubernetes API; EKS memberi ekosistem K8s penuh tetapi menambah biaya control plane. Untuk satu aplikasi kecil, EC2 + Docker sudah cukup.

Bagian E · Keamanan (topik 24–27)

24–27. Security Group, KMS, Secrets Manager, WAF

24. Security Group vs NACL. SG stateful, allow-only, melekat pada ENI. NACL stateless, bisa allow dan deny, melekat pada subnet. Untuk tugas: SSH hanya dari IP admin /32, HTTP/HTTPS dari 0.0.0.0/0.

25. KMS. Kelola kunci enkripsi untuk EBS, S3, RDS. Pisahkan kunci antar lingkungan.

26. Secrets Manager / SSM Parameter Store. Simpan password dan token, bukan di file .env yang ikut ter-commit. Aktifkan rotasi jika didukung.

27. WAF & Shield. WAF memfilter request (SQL injection, XSS, rate limit); Shield melindungi dari DDoS. Untuk lab, rate limit sederhana di Nginx sudah cukup.

contoh aturan Nginx — rate limit dasarlimit_req_zone $binary_remote_addr zone=web:10m rate=10r/s; server { location / { limit_req zone=web burst=20 nodelay; proxy_pass http://127.0.0.1:3000; } }

Bagian F · Arsitektur, reliability, dan biaya (topik 28–30)

28–30. Well-Architected, DR, dan FinOps

28. Enam pilar Well-Architected. Operational excellence, security, reliability, performance efficiency, cost optimization, sustainability. Gunakan sebagai daftar pertanyaan, bukan sertifikasi.

29. High availability & DR. Multi-AZ untuk produksi, backup lintas region untuk bencana. RTO/RPO menentukan strategi: backup & restore, pilot light, warm standby, multi-site.

30. FinOps. Tagging (Project, Owner, Environment), budget alarm, right-sizing, matikan instance saat tidak dipakai, hapus Elastic IP dan volume yatim.

Paling sering bocor: Elastic IP tidak terpasang, EBS snapshot lama, NAT Gateway menganggur, dan instance yang lupa di-stop. Periksa tagihan setiap hari selama masa tugas.

B. Membuat instance lewat Console

  1. Buka EC2 → Launch instance, isi Name tag uts-cloud-portfolio.
  2. Pilih AMI, instance type, dan key pair. Jika belum ada, buat baru dan unduh .pem.
  3. Pada Network settings, pilih VPC default, subnet publik, dan Auto-assign public IP: Enable.
  4. Buat Security Group baru; tambahkan SSH, HTTP, HTTPS sesuai tabel di atas.
  5. Storage 8–20 GiB gp3, lalu Launch. Tunggu status running dan 2/2 checks passed.
  6. Catat Public IPv4 address atau Public IPv4 DNS.
  7. Alokasikan Elastic IP, associate ke instance, lalu catat alamatnya.
Jangan pakai IP publik untuk SSH jika bisa dihindari. Batasi port 22 ke IP rumah/kampus. Jika IP berubah, edit inbound rule — jangan buka ke semua IP.

D. Menghubungkan lewat PuTTY (Windows)

  1. Buka PuTTYgen → Load file .pem (pilih “All files”) → Save private key sebagai .ppk.
  2. Buka PuTTY, Host Name: ec2-user@IP-PUBLIK atau ubuntu@IP-PUBLIK, Port 22.
  3. Connection → SSH → Auth → Credentials → pilih file .ppk.
  4. Session → Saved Sessions, simpan dengan nama UTS-EC2, lalu Open.
  5. Jika muncul peringatan host key, verifikasi fingerprint lalu Accept.

Linux, permission, dan SSH

Workflow build + deploy ke EC2

.github/workflows/deploy-ec2.ymlname: build-and-deploy on: push: branches: [main] workflow_dispatch: concurrency: group: deploy-ec2 cancel-in-progress: true jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: 20 cache: npm cache-dependency-path: app/package-lock.json - name: Install working-directory: app run: npm ci - name: Typecheck working-directory: app run: npm run typecheck - name: Build working-directory: app run: npm run build env: DATABASE_URL: postgres://placeholder deploy: needs: build runs-on: ubuntu-latest environment: production steps: - uses: actions/checkout@v4 - name: Siapkan SSH key run: | mkdir -p ~/.ssh echo "${{ secrets.EC2_SSH_KEY }}" > ~/.ssh/id_ed25519 chmod 600 ~/.ssh/id_ed25519 ssh-keyscan -H "${{ secrets.EC2_HOST }}" >> ~/.ssh/known_hosts - name: Sinkronkan situs statis run: | rsync -avz --delete \ --exclude '.git' --exclude 'node_modules' \ -e "ssh -o StrictHostKeyChecking=yes" \ ./index.html ./assets ./knowledge.html ./login.html ./dashboard.html \ "${{ secrets.EC2_USER }}@${{ secrets.EC2_HOST }}:/var/www/uts/" - name: Smoke test run: curl -fsS "http://${{ secrets.EC2_HOST }}/" | grep -qi "Muhammad Arya"

Aturan praktis

  • Bedakan CI (validasi tiap commit) dan CD (rilis ke lingkungan).
  • Gunakan environment protection untuk production agar ada approval.
  • Simpan kunci deploy khusus, bukan kunci pribadi; batasi izin di server.
  • Selalu ada langkah smoke test setelah deploy.
  • Rollback harus direncanakan: image tag sebelumnya atau symlink release.

Pola deploy atomik dengan symlink

di serverRELEASE=/var/www/releases/$(date +%Y%m%d%H%M%S) mkdir -p "$RELEASE" rsync -a --delete /tmp/upload/ "$RELEASE/" ln -sfn "$RELEASE" /var/www/uts-current sudo nginx -t && sudo systemctl reload nginx ls -1dt /var/www/releases/* | tail -n +6 | xargs -r rm -rf

Troubleshooting deployment

Urutan diagnosa yang saya pakai: DNS → jaringan → port → service → konfigurasi → aplikasi. Jangan mengubah konfigurasi sebelum tahu lapisan mana yang gagal.

GejalaPenyebab umumPerbaikan
Browser connection timed out Port 80 belum dibuka atau IP salah Periksa inbound rule Security Group dan Elastic IP
Connection refused Tidak ada service mendengar di port ss -tlnp | grep :80, start Nginx/Apache
Halaman default web server Docroot masih default Perbaiki root/DocumentRoot, reload service
CSS/JS 404, halaman tanpa gaya Folder assets/ tidak terunggah atau path salah Cek curl -I /assets/css/style.css, unggah ulang
403 Forbidden Permission atau index tidak ada chmod 755 direktori, 644 file, cek SELinux
502 Bad Gateway Aplikasi upstream mati atau port salah curl 127.0.0.1:3000, cek log aplikasi
504 Gateway Timeout Upstream lambat atau hang Naikkan proxy_read_timeout, cek query/CPU

Disk penuh Log membengkak df -h, du -sh /var/log/*, rotasi log
Domain tidak terbuka A record belum propagasi nslookup, tunggu TTL, cek nama record
