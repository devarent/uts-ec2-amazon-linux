Keputusan desain

  • SSH tidak dibuka ke semua orang. Rule port 22 dibatasi ke IP publik saya (/32), HTTP 80 dibuka untuk publik.
  • Tidak ada Access Key di dalam instance. Semua akses AWS memakai IAM Role yang menempel ke EC2.
  • Elastic IP dipakai agar alamat tidak berubah saat instance di-stop/start.
  • Database di private subnet (untuk RDS), hanya bisa diakses dari Security Group aplikasi.
  • Hemat biaya: instance di-stop setelah penilaian, lalu terraform destroy agar tidak ada tagihan berjalan.

Pipeline dari Laptop ke EC2

Alur ini yang saya siapkan untuk pengembangan berikutnya: begitu git push, image dibangun otomatis, dikirim ke container registry, lalu EC2 menarik versi terbaru.

  1. 1

    Build lokal & containerisasi

    Aplikasi diuji di localhost dulu, lalu dibungkus Docker dengan multi-stage build agar image kecil dan tidak membawa devDependency.

    FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public
EXPOSE 3000
CMD ["node", "server.js"]
  2. 2

    Jalankan bersama reverse proxy

    Nginx menerima trafik port 80 dan meneruskannya ke container aplikasi. Konfigurasi ini juga siap dipasangi TLS.

    services:
  app:
    build: .
    restart: unless-stopped
    environment:
      - NODE_ENV=production

  nginx:
    image: nginx:alpine
    restart: unless-stopped
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app
  3. 3

    Otomasi dengan GitHub Actions

    Setiap push ke main: build image, push ke registry, lalu jalankan perintah deploy lewat SSH (atau SSM tanpa membuka port 22).

    - name: Deploy ke EC2
  uses: appleboy/ssh-action@v1
  with:
    host: ${{ secrets.EC2_HOST }}
    username: ubuntu
    key: ${{ secrets.EC2_SSH_KEY }}
    script: |
      cd ~/app
      docker compose pull
      docker compose up -d --remove-orphans
      curl -fsS http://localhost/health || exit 1
  4. 4

    Infrastruktur sebagai kode

    EC2, Security Group, Key Pair, dan Elastic IP dibuat ulang kapan saja dengan Terraform — tidak ada lagi konfigurasi yang hanya "ada di kepala".

    terraform init
terraform plan -out tfplan
terraform apply tfplan
terraform output public_ip

# setelah dinilai
terraform destroy
  5. 5

    Monitoring, rollback, dan pembersihan

    Health check menentukan deploy berhasil atau tidak. Jika gagal, container lama dikembalikan; image lama dibersihkan agar disk tidak penuh.

    docker compose ps
docker compose logs --tail=50 app
docker compose down && docker compose up -d
docker image prune -af --filter "until=24h"
docker system df

Konsep Kunci — Catatan Belajar

Rangkuman pertanyaan yang paling sering muncul saat merancang sistem di AWS. Klik tiap bagian untuk membuka jawabannya.

1. Network & Security Architecture
  • Secret di dev vs produksi: di laptop boleh .env; di produksi pakai SSM Parameter Store / Secrets Manager, disuntikkan oleh platform (ECS) — jangan pernah commit kunci.
  • VPC isolation: resource backend di private subnet tanpa public IP, sehingga tidak bisa dirutekan dari internet.
  • Publik vs privat: DevTools hanya melihat request sampai API Gateway; isi VPC tidak terlihat dari browser.
  • IAM Policy vs Role: policy adalah dokumen aturan, role adalah "topi" yang dipakai service untuk mendapatkan kredensial sementara.
  • Cognito: User Pool = database pengguna + autentikasi (mengeluarkan JWT); Identity Pool = menukar token menjadi kredensial IAM sementara.
  • WAF & Shield: WAF memeriksa isi request (SQLi/XSS/bot), Shield menahan banjir trafik DDoS.
  • KMS: enkripsi at rest — data di disk selalu teracak, kunci dikelola KMS.
2. Compute & Microservices
  • EC2 vs Fargate: EC2 seperti punya mobil sendiri (rawat + bayar saat diam); serverless seperti naik taksi (bayar sesuai pakai).
  • Route publik vs terproteksi: GET /products boleh tanpa token; POST /orders wajib authorizer sehingga request tidak valid ditolak 401 sebelum masuk VPC.
  • API Gateway vs ALB: API Gateway di edge (auth, quota, validasi); ALB di dalam VPC (distribusi trafik & health check container).
  • ECR & ECS: build image → push ke ECR → ECS menarik image dan menjalankan task.
  • Lambda cold start: inisialisasi runtime membuat request pertama lambat; solusinya Provisioned Concurrency.
3. Database & Caching
  • RDS vs DynamoDB: RDS untuk transaksi relasional & ACID; DynamoDB untuk lookup key-value berskala besar.
  • Cache HTTP vs in-memory: cache di edge menyimpan respons final (read-only, publik); Redis menyimpan objek yang bisa berubah (session, counter stok).
  • Pencarian: LIKE '%kata%' tidak tahan typo dan berat di jutaan baris — gunakan OpenSearch untuk fuzzy match & ranking relevansi.
4. Messaging & Event-Driven
  • SNS + SQS: service pemesan cukup memublikasikan event lalu langsung membalas sukses; email & cart diproses asinkron.
  • SNS/SQS vs Kafka vs EventBridge: SQS untuk antrean tugas sekali pakai, Kafka untuk stream yang bisa diputar ulang, EventBridge untuk routing berbasis isi event.
  • Standard vs FIFO: Standard = throughput besar, at-least-once; FIFO = urutan ketat & tepat sekali, throughput terbatas.
  • Step Functions: mengorkestrasi langkah multi-service dengan retry dan compensation (Saga Pattern).
5. Storage, Frontend & Delivery
  • Rendering: SSR butuh compute (Lambda/ECS), bukan S3. SSG & CSR bisa sepenuhnya statis di S3; ISR adalah gabungan cache + rebuild di belakang.
  • Storage class: Standard untuk data panas, IA untuk arsip jarang dibuka, Glacier untuk retensi jangka panjang.
  • CloudFront: menaruh salinan aset di edge location sehingga latensi turun drastis untuk pengguna jauh dari region asal.
  • Route 53: bisa latency-based maupun failover, bukan sekadar memetakan nama ke satu IP.
  • VPC Endpoint: resource privat mencapai S3/DynamoDB lewat jalur privat, tanpa NAT Gateway dan tanpa internet publik.
6. DevOps, Observability & Architecture
  • Tiga pilar observability: logs (apa yang terjadi), metrics (seberapa parah), traces (di hop mana bermasalah).
  • Grafana vs Sentry: Grafana menjawab "sistem sedang rusak"; Sentry menjawab "baris kode mana penyebabnya".
  • Terraform vs CDK: Terraform deklaratif & multi-cloud (HCL); CDK memakai bahasa pemrograman lalu menghasilkan CloudFormation.
  • CodePipeline: Source → Build (CodeBuild + test + push image) → Deploy (CodeDeploy rolling update tanpa downtime).
  • Multi-AZ vs Multi-Region: Multi-AZ wajib untuk ketahanan satu data center; Multi-Region untuk bencana skala besar dan jauh lebih kompleks.
  • Well-Architected: Security, Reliability, Performance Efficiency, Cost Optimization, Operational Excellence, Sustainability.

Lab: WSL2 Ubuntu + PuTTY ke AWS EC2

Inilah jalur yang saya pakai untuk menghubungkan laptop Windows ke instance EC2: WSL2 Ubuntu untuk semua perintah Linux, dan PuTTY sebagai terminal SSH alternatif yang bisa dipakai saat presentasi.

1

Install WSL2 + Ubuntu

Jalankan di PowerShell (Administrator), lalu reboot bila diminta.

wsl --install -d Ubuntu
wsl --set-default-version 2
wsl -l -v

Setelah reboot, Ubuntu akan meminta username & password Linux (bebas, bukan password AWS).

2

Siapkan tools di dalam Ubuntu

Semua perintah berikut dijalankan di terminal Ubuntu (WSL2).

sudo apt update && sudo apt upgrade -y
sudo apt install -y curl git unzip openssh-client apache2

# verifikasi
lsb_release -ds
git --version
apache2 -v
3

Convert key pair .pem ke .ppk

AWS memberikan file .pem, sedangkan PuTTY memakai format .ppk.

  1. Buka PuTTYgen → Load → pilih file .pem (ubah filter ke All Files).
  2. Klik Save private key → simpan sebagai uts-cloud-key.ppk.
  3. Jangan pernah membagikan file ini. Simpan di folder pribadi, bukan di repository.
4

Konfigurasi sesi PuTTY

  1. Host Name: ubuntu@<PUBLIC-IP> (atau ec2-user@ untuk Amazon Linux).
  2. Port: 22 · Connection type: SSH.
  3. Connection → SSH → Auth → Credentials: pilih file .ppk tadi.
  4. Kembali ke Session, isi Saved Sessions dengan UTS-EC2, lalu klik Save.
  5. Klik Open → jawab yes pada prompt host key.

Alternatif dari WSL2 (tanpa PuTTY): ssh -i uts-cloud-key.pem ubuntu@<PUBLIC-IP> dengan chmod 400 uts-cloud-key.pem.

5

Pasang web server di EC2

Dari dalam sesi SSH, siapkan Apache2 (atau Nginx, pilih salah satu).

sudo apt update && sudo apt install -y apache2
sudo systemctl enable --now apache2
sudo systemctl status apache2 --no-pager

# buka firewall OS jika aktif
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
6

Deploy website ke document root

# dari laptop / WSL2
scp -i uts-cloud-key.pem -r index.html assets ubuntu@<PUBLIC-IP>:~/

# dari dalam EC2
sudo rm -f /var/www/html/index.html
sudo cp -r ~/index.html ~/assets /var/www/html/
sudo chown -R www-data:www-data /var/www/html
sudo chmod -R 755 /var/www/html
curl -I http://localhost
7

Verifikasi lewat Public IP

Buka browser (bukan localhost) dan pastikan halaman tampil lengkap dengan foto & CSS.

# uji dari laptop
curl -I http://<PUBLIC-IP>
curl -o NUL -w "%{http_code}\n" http://<PUBLIC-IP>/assets/css/style.css

Jika CSS 404, berarti folder assets belum ikut ter-copy ke /var/www/html.

8

Naik level: Docker, Terraform, Helm

Setelah situs statis berjalan, lab dilanjutkan ke containerisasi dan orkestrasi.

# Docker
docker build -t web-uts:v1 .
docker run -d -p 8080:80 web-uts:v1

# Terraform
terraform init && terraform plan && terraform apply

# Kubernetes + Helm
kind create cluster --name uts
helm upgrade --install web ./helm/nextjs-app --set image.tag=latest
kubectl get pods,svc,ingress
